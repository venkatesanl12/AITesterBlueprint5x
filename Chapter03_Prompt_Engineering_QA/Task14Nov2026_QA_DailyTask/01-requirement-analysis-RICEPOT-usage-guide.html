Requirement Analysis — RICE-POT reference guide

Template file01-requirement-analysis-RICEPOT.md
FrameworkRICE-POT
TaskRequirement analysis & testability review
Guide01 of 17

What it does. Takes a PRD, user story, Jira ticket, or client email and turns it into a requirement register where every row cites its source, every testability verdict is justified, and every hole is logged as a gap — before a single test case is written.

Use when

You received raw requirement material and need to know what is testable, what is ambiguous, and what is missing. Also use it as the first step of any new feature test cycle.

Skip when

The requirement is already decomposed into numbered, testable statements and you only need cases — go straight to 02-test-case-design-RICEPOT.md.

1

Read the framework before you paste anything

Each letter is a section of the prompt. Knowing which letter owns which behaviour tells you where to edit when the output goes wrong — instead of rewriting the whole prompt.

R
RoleWho the model is and the standard it is held to.
I
InstructionsThe numbered procedure. This is the part that must not be softened.
C
ContextThe only section you edit per run — product, sources, constraints.
E
ExampleA locked sample row showing the exact expected shape.
P
ParametersAnti-hallucination rules: determinism, exact fallback phrases, allowed values.
O
OutputFixed sections in a fixed order with fixed columns.
T
ToneHow the answer should read. No praise, no filler.
Rule of thumb. R, I, E, P, O and T stay as written. Only C — Context changes between runs. If you find yourself editing I, P or O, the template is being used for the wrong task.
2

Prepare the inputs first

Gather the sources before touching the prompt. The template forbids inventing requirements, so anything you do not hand over simply becomes a gap.

  • Source material — the PRD section, story, ticket, email, or screenshot you will cite.
  • Section references — note the clause numbers, because every row must cite one.
  • Constraints — release window, platform, regulatory rules, or write “none supplied”.
  • Scope line — state the boundary, e.g. “login only”, so the register stops where the analysis stops.

Most common mistake. Pasting a whole PRD but describing it as “the login module”. Requirement IDs then drift into other modules and the summary counts lie. Paste what you scope, scope what you paste.
4

Audit the output against the contract

The response must contain all five sections, in this order, with these shapes. If a section is missing or reshaped, the run failed — point the model at the specific section and re-run.

SectionRequiredShape
Requirement RegisterYesMarkdown table, 7 columns, stable REQ-AREA-NNN IDs
Gap RegisterYesMarkdown table, 6 columns, every ID prefixed GAP-
ContradictionsYes4 columns; may state “None identified” but may not be omitted
Clarifying QuestionsYesNumbered list, max 10, highest impact first, each tied to a GAP ID
Analysis SummaryYesCounts only: total, testable, partial, not testable, open gaps

The requirement register columns are fixed: Req ID, Requirement Statement, Source, Type, Testable, Acceptance Criteria, Notes. Type is one of Functional, Non-Functional, Data, Security, Business Rule.

6

Run the self-check before you trust the output

Six checks, straight from the template. Any failure means fix that section — do not re-prompt from scratch.

  • Every row cites a real source section from the supplied material.
  • No requirement appears that was not stated in the source.
  • Every Partial / No testability row links to a GAP ID.
  • Gaps describe what is missing, not a guess at the answer.
  • Questions are answerable by a product owner, not by another AI run.
  • Summary counts match the table row counts exactly.
Fastest sanity check. Count the register rows, count the summary total, count the gap rows. If those three do not reconcile, the run is not finished — however polished the prose looks.
7

Fix the failure, not the whole prompt

SymptomRule breachedCorrection to send
Requirements appear that you never supplied.No source, no row.“Delete any row without a cited source. Re-check the register.”
Missing detail was filled in as “typical behaviour”.No assuming standard behaviour.“Replace that text with exactly: Insufficient information to determine.”
New acceptance criteria were authored.Only source-stated criteria.“Keep only criteria quoted from the source. Move the rest to the gap register.”
Testability says Partial but no gap exists.Every Partial maps to a gap.“Add the missing GAP row or change the verdict. No third option.”
A deduced detail was written as fact.Inference labelling.“Label it exactly: Inference (low confidence).”
Fifteen clarifying questions returned.Max 10, highest impact first.“Cut to the 10 that block testing. Drop the rest.”

9

Turn it into a skill

Create skills/requirement-analysis/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: requirement-analysis
description: Analyse a PRD, user story, or ticket and produce a traceable requirement register with a gap register, contradictions, and clarifying questions. Use when requirements must be understood or challenged before test design.
---

Trigger phrases: “analyse these requirements”, “requirement review”, “is this testable”, “extract requirements from this PRD”, “what’s missing in this story”.

Procedure: read all sources → requirement register → gap register → contradictions → questions → summary → run self-check.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
