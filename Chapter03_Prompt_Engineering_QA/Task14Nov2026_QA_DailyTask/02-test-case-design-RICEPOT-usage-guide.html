Guide02 of 17

What it does. Turns an approved requirement set into executable test cases a new team member could run without asking a question — each case traced to one requirement, each expected result observable, each unknown marked Blocked against a GAP ID.

Use when

You have approved requirements and need cases that can be executed, reviewed, and traced. This is the standard step after requirement analysis and before execution.

Skip when

Requirements are still ambiguous or untestable — run 01-requirement-analysis-RICEPOT.md first, or you will be writing cases that cannot be asserted.

1

Read the framework before you paste anything

Each letter is a section of the prompt. The Instructions section is where the case-design discipline lives; the Parameters section is where hallucination is fenced off.

R
RoleWho the model is and the standard it is held to.
I
InstructionsThe numbered procedure. This is the part that must not be softened.
C
ContextThe only section you edit per run — product, sources, constraints.
E
ExampleA locked sample row showing the exact expected shape.
P
ParametersAnti-hallucination rules: determinism, exact fallback phrases, allowed values.
O
OutputFixed sections in a fixed order with fixed columns.
T
ToneHow the answer should read. No praise, no filler.
Rule of thumb. R, I, E, P, O and T stay as written. Only C — Context changes between runs. If you find yourself editing I, P or O, the template is being used for the wrong task.
2

Prepare the inputs first

The template can only design cases for what you supply. Anything missing becomes a Blocked case, which is correct behaviour but slows the cycle down.

  • Approved requirements with IDs — if they have no IDs, run template 01 first so IDs exist to trace against.
  • Existing test cases — so the model does not duplicate them, and can say so in Design Notes.
  • Environment details — URL, browser, build. This shapes the steps.
  • Target case count if you have one, so coverage is deliberate rather than endless.
  • Credentials — as placeholders only. Never paste real ones.

4

Audit the output against the contract

Four sections, fixed order. The Test Cases table is ten columns wide — if any column is missing, the case cannot be executed or traced.

SectionRequiredShape
Coverage MapYesTable, 3 columns, one row per requirement
Test CasesYesTable, 10 columns, fixed order, unique sequential IDs
Blocked CasesYesTable, 3 columns; may say “None”
Design NotesYesShort bullets on assumptions avoided and exclusions

Fixed values: Type is Positive / Negative / Boundary / Security / Access Control; Confidence is Verified / Inference (low confidence) / Blocked; Priority is P1–P4. Nothing outside these lists is valid.

6

Run the self-check before you trust the output

Seven checks from the template. Run them before the cases leave your machine — a duplicate or an unobservable expected result costs a full execution cycle.

  • Every requirement in the coverage map has at least one case or is marked Not Covered.
  • No two cases test the identical check.
  • Steps are literal — no “verify appropriate behaviour” phrasing.
  • Expected results describe something a tester can observe on screen or in a response.
  • No case marked Passed or Failed — execution has not happened.
  • All credentials are placeholders.
  • Blocked cases each cite a GAP ID and say what is missing.
Fastest sanity check. Read each expected result aloud. If it is not something you could point at on screen or in a response body, the case is not executable yet.
7

Fix the failure, not the whole prompt

SymptomRule breachedCorrection to send
Two checks merged into one case.Do not merge two checks.“Split into one check per case and renumber sequentially.”
Expected result says “should work correctly”.Observable behaviour only.“Replace with the observable screen or response outcome.”
A case is marked Passed.Execution has not happened.“Use Verified / Inference / Blocked only. Status belongs to template 04.”
Duplicate of an existing case appears.Do not duplicate supplied cases.“Drop it and note the existing case ID in Design Notes.”
Blocked case with no GAP ID.Blocked cases cite a gap.“Add the GAP ID or make the expected result observable.”
A case covers a feature the requirements never mention.No cases outside the requirements.“Remove the case and list the excluded feature in Design Notes.”

Turn it into a skill

Create skills/test-case-design/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: test-case-design
description: Generate traceable, executable test cases from approved requirements, with a coverage map, blocked-case register, and anti-hallucination labels. Use when designing functional test cases for a module or ticket.
---

Trigger phrases: “write test cases for”, “design tests for this story”, “generate functional test cases”, “cover this requirement”.

Procedure: read requirements → coverage map → cases in positive/negative/boundary/access order → blocked register → design notes → self-check.
