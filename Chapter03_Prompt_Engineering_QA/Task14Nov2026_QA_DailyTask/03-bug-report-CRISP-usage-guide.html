TaskSingle defect report for a developer
Guide03 of 17

What it does. Turns what you observed into one defect report a developer can reproduce without asking you anything — environment, numbered atomic steps, expected anchored to a requirement, actual as pure observation, and severity with a rationale.

Use when

You found one defect and it needs to be filed properly. The report is the artefact a developer, a triager, and a release manager all read.

Skip when

You are logging many defects at once — use 05-defect-tracking-CRISP.md so they share one consistent register.

1

Read the framework before you paste anything

CRISP puts the raw observation in Context and the discipline in Instructions. The Style and Parameters sections are what keep the report short and free of diagnosis.

C
ContextThe situation and raw facts you supply. Per-run editable surface.
R
RoleThe judgement role the model takes on for this document.
I
InstructionsNumbered rules plus the explicit Do NOT list.
S
StyleHow terse, how structured, what vocabulary is banned.
P
ParametersHard limits: allowed scales, missing-data wording, length caps.
Rule of thumb. The Role decides the judgement, the Parameters decide the limit. If the output wavers, tighten the Parameters — not the Role. Only C — Context changes between runs.
2

Prepare the inputs first

The report can only be as good as the observation you supply. Fill these in before you touch the prompt — gaps here become “Not supplied” in the output.

  • Exact steps you took — the literal actions, in order, including the data used.
  • What you saw — the observation, written without interpretation.
  • The requirement violated — REQ ID plus short statement, so Expected can be anchored.
  • Reproducibility — N out of M attempts, including the ones that did not reproduce.
  • Environment and evidence — browser, OS, build, date-time; screenshots, video, console, network.

Most common mistake. Writing the observation as a diagnosis (“validation is broken”). That pulls a root cause into the report and the developer stops reading the steps. Report what appeared; let them diagnose.
4

Audit the output against the contract

Eleven required fields, in this order. A missing field is written as “Not supplied.” or “Not provided.” — never left blank and never guessed.

SectionRequiredShape
TitleYes[Area] — [Action] — [Problem], ≤120 characters
EnvironmentYes“Not supplied.” where unknown
PreconditionsYesEnough to recreate the starting state
Test DataYesPlaceholders only
Steps to ReproduceYesNumbered, one action per step
Expected ResultYesTied to a requirement ID
Actual ResultYesObservation only
ReproducibilityYesN/M
Severity + rationaleYesMarked provisional when the requirement is unclear
Priority + rationaleYesOne-line business reason
AttachmentsYesOr “Not provided.”

Severity scale is Critical / High / Medium / Low; priority is P1–P4. Maximum 500 words — if you are over, cut background, never steps.

5

What a good run looks like

Filled excerpt from the template — the title follows the three-part form, the expected result cites the requirement, and the unknown validation text is named as a gap rather than invented.

FieldContent
TitleLogin — Submit with empty password — No validation feedback shown
Expected ResultPer REQ-002, password is mandatory; submission with an empty password should be rejected and the user should see validation feedback. Exact validation message: Insufficient information to determine. (GAP-02)
Actual ResultThe form submitted and no visible validation feedback was displayed anywhere on the page.
SeverityHigh (provisional) — mandatory-field enforcement appears absent, allowing malformed submissions. Provisional because the required validation behaviour is not fully specified.
Reproducibility3 out of 3 attempts

Note the report never says why it happened. No root cause, no guessed error code, no invented log line.

6

Run the self-check before you trust the output

Seven checks. These exist because the two most common defect-report failures are compound steps and invented diagnosis — both are caught here.

  • Title follows the three-part form and fits 120 characters.
  • Every step is a single action.
  • Expected result cites the requirement it comes from.
  • Actual result contains no diagnosis or root-cause claim.
  • Severity has a rationale and is marked provisional if the requirement is vague.
  • No real credentials, emails, or customer data appear.
  • Word count is under 500.
Fastest sanity check. Hand the steps to someone who did not see the defect. If they ask a question before reproducing it, a step is missing.
7

Fix the failure, not the whole prompt

SymptomRule breachedCorrection to send
Steps contain compound actions (“enter email and submit”).One action per step.“Split into atomic numbered steps.”
Actual result contains a diagnosis.Observation only, no root cause.“Replace with what appeared on screen. Remove the explanation.”
Environment left blank.“Not supplied.” when unknown.“Write Not supplied. in that field.”

The defect ID you receive after filing is the key that travels onward. Quote it in the execution record, the triage table, and the RTM reverse trace — never re-title the defect in each place.

9

Turn it into a skill

Create skills/bug-report/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: bug-report
description: Write a concise, reproducible bug report with environment, numbered steps, expected vs actual, reproducibility, and provisional severity with rationale. Use when a defect has been observed and must be filed.
---

Trigger phrases: “write a bug report”, “log this defect”, “file a bug for this”, “create a Jira bug”.

Procedure: collect context → title → environment → preconditions → steps → expected → actual → reproducibility → severity/priority → attachments → self-check.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
