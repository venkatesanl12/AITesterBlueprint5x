Test Case Execution — CLEAR reference guide

FrameworkCLEAR
TaskEvidence-backed execution record
Guide04 of 17

What it does. Records what actually happened when you ran a suite: per-step status, evidence reference, case-level roll-up, failures, and blockers — with a hard rule that nothing is Passed without evidence.

Use when

You are executing an existing suite against a build and need a record that survives audit. This is the document a release decision is argued from.

Skip when

The test cases do not exist yet — use 02-test-case-design-RICEPOT.md. Recording execution of cases you invented is not execution.

1

Read the framework before you paste anything

CLEAR exists to stop awarded passes. The Limits section lists the five allowed statuses and the rule that missing evidence means missing evidence — not a pass.

C
ContextWhat is being run, on which build, with which evidence.
L
LimitsThe fence: allowed statuses, allowed scope, what may not be invented.
E
ExamplesSample rows showing the exact status and evidence shape.
A
ActionThe single deliverable you want returned.
R
ReviewThe checks the model must pass before returning the answer.
Rule of thumb. Limits are the whole point of CLEAR — they stop the model awarding an unearned pass. Only C — Context changes between runs; never relax L to get a longer answer.
2

Prepare the inputs first

Collect the evidence before the session, not after. Anything you cannot evidence will be recorded as “No evidence supplied.”

  • Test cases with steps — the actual cases being run, with their IDs. Execution cannot add or rewrite them.
  • Build and environment — build ID, URL, browser version, OS, device.
  • Execution window — start and end time, so duration is defensible.
  • Evidence captures — screenshots, logs, HAR, video, labelled so they can be referenced per step.
  • Known blockers — missing accounts, unavailable services, so Blocked rows have a named cause.

Most common mistake. Supplying case IDs without the steps. The model cannot record a per-step log against steps it cannot see, so every case comes back as Blocked — which is honest but useless.
4

Audit the output against the contract

Four sections, fixed order. The step-level log is the evidence; the case-level result is the roll-up; both must agree.

SectionRequiredShape
Execution SummaryYesTotal / Passed / Failed / Blocked / Not Run / Skipped + pass rate
Step-Level LogYesTC ID | Step | Action | Expected | Status | Evidence
Case-Level ResultYesTC ID | Overall Status | Observed Result | Defect Ref | Notes
FailuresYesTC ID | Step | Expected | Actual | Suggested Severity; may say “None”
BlockersYesTC ID | What Blocked Execution | Owner To Unblock; may say “None”

Allowed statuses, exactly five: Passed / Failed / Blocked / Not Run / Skipped. No status outside that list exists, and summary counts must equal table rows.

6

Run the self-check before you trust the output

Six checks. The first two are the ones that make the record audit-proof — evidence per step, and one row per supplied case.

  • Every supplied test case appears exactly once in the case-level result.
  • Every Passed case has evidence against each of its steps.
  • Every Failed case has a concrete observed actual result.
  • Every Blocked case names the blocker and the owner who can unblock it.
  • No status outside the five allowed values.
  • Summary arithmetic matches the tables.
Fastest sanity check. Pick any Passed case and click through its evidence references. If a step has no artefact, that case is not Passed — it is Not Run.
7

Fix the failure, not the whole prompt

SymptomRule breachedCorrection to send
A case is Passed with no evidence for a step.No unearned pass.“Downgrade to Not Run or supply the evidence reference for that step.”
A case appears that was not supplied.Use only the supplied cases.“Remove it and list it as out of scope.”
A status reads “In Progress” or “Pending”.Five allowed statuses only.“Map to Passed / Failed / Blocked / Not Run / Skipped.”
A step could not run but the case is Passed.Blocked, not Passed.“Set the case to Blocked and name what blocked it.”
A defect ID appears that you never supplied.Do not assign defect IDs.“Replace with: Defect not yet raised.”
Summary pass rate does not match the tables.Arithmetic must reconcile.“Recount from the case-level table and recompute the rate.”
8

Where the output goes next

Bug report03-bug-report-CRISP.mdTurn each failure row into a reproducible report.
RTM06-rtm-RICEPOT.mdAttach execution status to each requirement for traceability.
Status report13-status-report-STAR.mdRoll execution counts into stakeholder reporting.

Failures move into bug reports; blocked cases move into the gap analysis or environment queue. Nothing should sit in this record unactioned — a Blocked row without an owner is just a delay with paperwork.

9

Turn it into a skill

Create skills/test-case-execution/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: test-case-execution
description: Produce an evidence-backed execution record — per-step log, case-level status, failures, and blockers — using only the supplied test cases and without inventing results. Use when running a test suite against a build.
---

Trigger phrases: “record execution results”, “log test run”, “execution report for this build”, “run these test cases and record status”.

Procedure: load cases → record per step → roll up case status → list failures → list blockers → verify no unearned Passed → self-check.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
