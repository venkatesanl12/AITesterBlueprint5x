Defect Tracking — CRISP reference guide

Template file05-defect-tracking-CRISP.md
FrameworkCRISP
TaskDefect log hygiene across a cycle
Guide05 of 17

What it does. Normalises defects from several testers into one register with consistent states, computed age, ageing flags, duplicate links, and summaries by severity and module — so nothing is untracked, duplicated, or ageing silently.

Use when

You maintain the defect log across a cycle and need one row per defect that a release manager can read without asking which tester wrote it.

Skip when

You are filing a single detailed defect — use 03-bug-report-CRISP.md. A register row is not a reproduction guide.

1

Read the framework before you paste anything

CRISP makes the QA lead the role: the job is hygiene, not judgement of importance. Phase gives the register its consistency; triage decides priority elsewhere.

C
ContextThe situation and raw facts you supply. Per-run editable surface.
R
RoleThe judgement role the model takes on for this document.
I
InstructionsNumbered rules plus the explicit Do NOT list.
S
StyleHow terse, how structured, what vocabulary is banned.
P
ParametersHard limits: allowed scales, missing-data wording, length caps.
Rule of thumb. The Role decides the judgement, the Parameters decide the limit. If the output wavers, tighten the Parameters — not the Role. Only C — Context changes between runs.
2

Prepare the inputs first

The register is only as complete as the list you paste. Missing fields are allowed — they are reported as data-quality gaps rather than filled in.

  • The defect list itself — paste the raw table or export, even if fields are inconsistent.
  • Reporting period and build — so age and scope are bounded.
  • Owner roster — names or roles, so ownership can be assigned from what exists.
  • SLA days — the ageing threshold. Default is 5 days if you do not state one.
  • Tracker of record — Jira, Azure DevOps, or sheet, so the row shape matches your export.

4

Audit the output against the contract

Five sections. The register is the record; the two summaries are the readout; the ageing and data-quality sections are the actions.

Allowed states, exactly: New / Open / In Progress / Fixed / Retest / Closed / Reopened / Deferred / Rejected. Supplied defect IDs are preserved verbatim — never renumbered. Main table sorts by severity, then age descending.

6

Run the self-check before you trust the output

Six checks. ID preservation and duplicate linking are the two that keep the register trustworthy across testers.

  • Every supplied defect appears exactly once in the register.
  • All states come from the allowed list.
  • Age is computed, not guessed, from the raised date.
  • Ageing flags use the stated SLA, consistently.
  • Duplicates are linked, not deleted.
  • Severity totals equal register row totals.
Fastest sanity check. Compare the supplied list length to the register row count. If they differ, either a duplicate was deleted or a defect was merged — both are contract violations.
7

Fix the failure, not the whole prompt

SymptomRule breachedCorrection to send
Defect IDs were renumbered.Preserve supplied IDs.“Restore the original IDs and re-link duplicates.”
A duplicate row was deleted.Link duplicates, never delete.“Restore the row and add the duplicate link in both directions.”
Age looks estimated.Compute from the raised date.“Recompute every age from Raised Date to the reporting date.”
Defect marked Fixed with no evidence.No closure without evidence.“Set it back to Open and name the missing evidence.”
Severity changed silently.State the change and reason.“Add a note naming the old severity, the new one, and why.”
Ageing flags disagree with the SLA.One stated threshold.“Recompute all flags against the SLA days supplied.”

9

Turn it into a skill

Create skills/defect-tracking/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: defect-tracking
description: Normalise defects into a single tracking register with consistent states, computed age, ageing flags, duplicate links, severity and module summaries, and data-quality gaps. Use when maintaining a defect log across a test cycle.
---

Trigger phrases: “update the defect log”, “defect tracking report”, “which bugs are ageing”, “defect summary by severity”.

Procedure: ingest defects → normalise rows → dedupe/link → compute age → flag ageing → summarise by severity and module → list data gaps → self-check.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
