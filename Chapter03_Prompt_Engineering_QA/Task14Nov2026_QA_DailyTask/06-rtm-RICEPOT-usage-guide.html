FrameworkRICE-POT
TaskAudit-ready requirement coverage
Guide06 of 17

What it does. Builds a matrix proving every requirement is covered by tests, has an execution status, and has its failures linked — plus the reverse defect trace and orphan lists that make it audit-ready rather than decorative.

Use when

You must prove coverage before a release gate. Also use it when someone asks “which requirements have no tests?” and the answer must be evidence, not memory.

Skip when

The requirements themselves are unclear or unnumbered — run 01-requirement-analysis-RICEPOT.md first. An RTM over unstable requirements documents fiction.

1

Read the framework before you paste anything

The Role is a QA lead building an audit artefact. That framing matters: every cell must be provable, so the Parameters forbid inferred coverage and invented IDs.

Rule of thumb. R, I, E, P, O and T stay as written. Only C — Context changes between runs. If you find yourself editing I, P or O, the template is being used for the wrong task.
2

Prepare the inputs first

Three artefacts in, one matrix out. If any of the three is missing, the matrix will say so in the coverage verdict — which is honest but not useful at a release gate.

  • Requirements with IDs — PRD, Jira, or spec. IDs are the spine of the matrix.
  • Test cases — with the requirement each one verifies, or enough detail to map them.
  • Execution results — latest per case, or the matrix can only report Not Executed.
  • Defects — so failures link forward and defects link back.
  • Release and build — the gate this matrix is evidence for.

4

Audit the output against the contract

Five sections. The forward view and the reverse view must agree — that agreement is what makes the matrix auditable.

SectionRequiredShape
Requirement → Test → DefectYes6 columns, one row per requirement
Reverse TraceYes4 columns, one row per defect
Orphaned RequirementsYes3 columns; may say “None”
Orphaned Test CasesYes3 columns; may say “None”
Coverage SummaryYesCounts + coverage % + execution %

Coverage verdicts are Covered / Partial / Not Covered; execution status is All Passed / Mixed / All Failed / Not Executed / Partially Executed. Never report 100% unless every requirement has at least one executed passing case.

6

Run the self-check before you trust the output

Six checks. The reconciliation ones (row count, reverse view, percentages) are what an auditor will independently recompute.

  • Requirement count equals RTM row count.
  • No requirement marked Covered with a Not Executed test case.
  • Every defect in the forward view appears in the reverse view.
  • Orphan lists generated by actual comparison, not assumption.
  • Coverage and execution percentages recomputed, not asserted.
  • No invented IDs anywhere.
Fastest sanity check. Recompute the coverage percentage from the row counts yourself. If your arithmetic differs from the summary, the summary was written before the table.
7

Fix the failure, not the whole prompt

SymptomRule breachedCorrection to send
Coverage inferred from a test case title.Evidence, not titles.“Remove the verdict until a case explicitly asserts that requirement.”
Requirement marked Covered with one Not Executed case.No coverage without execution.“Downgrade to Partial and state which case is not executed.”
100% coverage claimed.Requires an executed passing case each.“Recompute and list requirements with no executed passing case.”
A defect is missing from the reverse view.Every defect traces back.“Add the reverse row with its impacted requirement IDs.”
Two requirements collapsed into one row.One row per requirement.“Split them and map their cases separately.”
Test IDs appear that were never supplied.No invented IDs.“Replace with Not supplied. and flag the row.”

9

Turn it into a skill

Create skills/requirements-traceability-matrix/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: requirements-traceability-matrix
description: Build an audit-ready RTM mapping requirements to test cases, execution status, and defects, with reverse defect trace, orphan detection, and computed coverage. Use when proving coverage before a release gate.
---

Trigger phrases: “build an RTM”, “traceability matrix”, “prove requirement coverage”, “which requirements are untested”.

Procedure: parse requirements → map cases → derive execution status → link defects → compute coverage → orphan analysis → reverse trace → summary → self-check.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
