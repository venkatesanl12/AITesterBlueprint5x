# 06 — Requirements Traceability Matrix (RTM)

> **Framework:** RICE-POT
> **Use when:** You must prove every requirement is covered by tests, executed, and that failures are linked — typically before a release gate.
> **Skip when:** Requirements themselves are unclear — run `01-requirement-analysis-RICEPOT.md` first.

---

## Prompt Template

```text
### R — Role
You are a QA lead building an audit-ready traceability matrix. Every cell must
be provable from the supplied artefacts.

### I — Instructions
1. Build one row per requirement. Never collapse two requirements into one row.
2. Use the requirement ID from the source. If none exists, create REQ-<AREA>-<NNN> and flag it.
3. List every test case that verifies the requirement, comma-separated, preserving given IDs.
4. Record the latest execution status per requirement, derived from its test cases:
   All Passed / Mixed / All Failed / Not Executed / Partially Executed.
5. Link every defect to the requirement it impacts.
6. Compute coverage per requirement as Covered / Partial / Not Covered.
7. Add a defect-to-requirement reverse view so nothing is orphaned.
8. List orphaned test cases (tests with no requirement) and orphaned requirements (no tests).

Do NOT:
- Infer coverage from a test case title alone.
- Mark a requirement Covered when any of its test cases is Not Executed.
- Invent defect IDs, test IDs, or execution results.

### C — Context
- Product / release: [PRODUCT, RELEASE, BUILD]
- Requirements source: [PRD / JIRA / SPEC — with IDs]
- Test cases supplied: [PASTE OR ATTACH]
- Execution results supplied: [PASTE OR "Not executed yet"]
- Defects supplied: [PASTE OR "None"]

### E — Example
| REQ-001 | Registered users log in with valid credentials | VWO-LOGIN-TC-001, TC-002 | All Passed | Covered | — |
| REQ-002 | Email and password are mandatory | VWO-LOGIN-TC-004 | All Failed | Covered | DEF-101 |
| REQ-003 | Session timeout enforced | Not supplied | Not Executed | Not Covered | — |

### P — Parameters
- Output must be deterministic.
- Missing data: "Not supplied."
- Unprovable coverage: "Insufficient information to determine."
- Never report 100% coverage unless every requirement has ≥1 executed passing case.

### O — Output
1. **RTM (Requirement → Test → Defect)** — Req ID | Requirement | Test Case IDs | Execution Status | Coverage | Defect IDs
2. **Reverse Trace (Defect → Requirement)** — Defect ID | Severity | Impacted Req IDs | Affected Test Cases
3. **Orphaned Requirements** — Req ID | Requirement | Why Untested
4. **Orphaned Test Cases** — TC ID | Summary | Why Orphaned
5. **Coverage Summary** — total requirements, covered, partial, not covered, coverage %, execution %, defect density per requirement

### T — Tone
Audit-ready. Neutral. No recommendations unless asked.
```

## Filled Example

```text
### O — Output (excerpt)
| REQ-002 | Email and password are mandatory | VWO-LOGIN-TC-004, TC-005 | All Failed | Covered | DEF-101 |
| REQ-004 | Successful login opens the dashboard | VWO-LOGIN-TC-001 | All Passed | Covered | — |

### Coverage Summary
Requirements: 4 | Covered: 2 | Partial: 1 | Not Covered: 1 | Coverage: 75%
Execution: 3 of 4 requirements executed (75%) | Open defects linked: 1
```

---

## Output Contract

| Section | Required | Shape |
|---|---|---|
| Requirement → Test → Defect | Yes | 6 columns, one row per requirement |
| Reverse Trace | Yes | 4 columns, one row per defect |
| Orphaned Requirements | Yes (or "None") | 3 columns |
| Orphaned Test Cases | Yes (or "None") | 3 columns |
| Coverage Summary | Yes | Counts + two percentages |

Rules: no requirement row without a coverage verdict; every defect appears in the reverse view; coverage % must reconcile with row counts.

---

## Self-Check

- [ ] Requirement count equals RTM row count.
- [ ] No requirement marked Covered with a Not Executed test case.
- [ ] Every defect in the forward view appears in the reverse view.
- [ ] Orphan lists generated by actual comparison, not assumption.
- [ ] Coverage and execution percentages recomputed, not asserted.
- [ ] No invented IDs anywhere.
