Daily Scrum Notes — STAR reference guide

FrameworkSTAR
TaskStand-up update plus durable note
Guide10 of 17

What it does. Converts raw daily activity into two artefacts at once: a spoken update under 60 seconds, and a written note that keeps the evidence, owners, and blocker ages that a verbal update loses.

Use when

You are writing your daily stand-up update, or keeping a team scrum log that must still be useful three weeks later.

Skip when

The audience is a stakeholder rather than the team — use 13-status-report-STAR.md, where metrics and trend replace task granularity.

1

Read the framework before you paste anything

STAR is native to stand-up: Done / Doing / Blockers maps cleanly onto Situation, Task, Action, Result when you keep the evidence attached.

S
SituationThe release, change, budget and constraints you supply.
T
TaskThe one outcome required, stated in a sentence.
A
ActionThe ordered analysis steps the model must perform.
R
ResultThe numbered deliverable sections and their shape.
Rule of thumb. STAR is a planning and reporting frame, so the numbers live in S and the contract lives in R. Only S — Situation changes between runs.
2

Prepare the inputs first

The written note is only as searchable as the raw material you paste. Ticket IDs, case IDs, and build status are what make it survive.

  • Date and sprint — the note must be findable later.
  • Your assigned work — tickets or case IDs owned, so progress is anchored.
  • Build status — which build today’s activity was against.
  • Raw notes — ticket updates, execution results, defect IDs. Paste them; do not pre-summarise.
  • Sprint goal — one line, so the goal impact verdict is possible.
3

Most common mistake. Pre-summarising the raw notes into “worked on login”. The model then has nothing to evidence, and the written note becomes a diary entry rather than a record.
4

Audit the output against the contract

Five sections. The spoken update is for the room; the written table is for the record. Both come from the same evidence.

SectionRequiredShape
Spoken UpdateYesThree sentences maximum — Done / Doing / Blockers
Written NotesYesTable: Item | Type | Evidence | Owner | Status
Sprint Goal ImpactYesOn track / At risk / Blocked + reason
BlockersYesBlocker | Owner | Days Open | Needed By; may say “None”
TomorrowYesNumbered actions with owners

Every written row needs evidence — a case ID, a checklist, a defect ID, or an execution result. “Testing in progress” is not an evidence value.

6

Run the self-check before you trust the output

Six checks. The 60-second read-aloud test catches more bloat than any rule about word counts.

  • Every Done item names a concrete artefact or ID.
  • Every Doing item names the next action, not a vague activity.
  • Blockers include owner and days open.
  • Sprint goal verdict is consistent with the notes.
  • Spoken version reads aloud in under 60 seconds.
  • No invented counts or IDs.
Fastest sanity check. Read the spoken update aloud with a timer. If you need the written table to make sense of it, it is too long.
7

Fix the failure, not the whole prompt

SymptomRule breachedCorrection to send
A Doing row says “testing in progress”.Name what is being tested.“Replace with the concrete artefact and case IDs.”
A Done item has no evidence.Evidence required.“Move it to Doing and state what evidence is missing.”
A blocker has no age.Days open computed.“Compute from the date it was first raised.”
The spoken update runs to eight sentences.Three sentences maximum.“Cut to three; move detail into the written table.”
Counts appear that you never supplied.No invented numbers.“Write Not supplied. and remove the count.”
Sprint goal verdict contradicts the blockers.Consistency.“Re-derive the verdict from the blocker rows.”

9

Turn it into a skill

Create skills/daily-scrum-notes/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: daily-scrum-notes
description: Turn raw daily QA activity into a short spoken stand-up update plus a durable written scrum note with evidence, blockers, sprint-goal impact, and tomorrow’s actions. Use when preparing a daily stand-up or maintaining a scrum log.
---

Trigger phrases: “daily scrum notes”, “stand-up update”, “what do I say in standup”, “scrum log for today”.

Procedure: ingest raw activity → classify Done/Doing/Blockers with evidence → spoken summary → written table → goal impact → blockers with age → tomorrow’s actions → self-check.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
