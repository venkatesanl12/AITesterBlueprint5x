Gap Analysis — RICE-POT reference guide

Template file11-gap-analysis-RICEPOT.md
FrameworkRICE-POT
TaskTyped gap register and coverage before/after
Guide11 of 17

What it does. Compares a baseline artefact against what actually exists and reports every hole with a type, an impact rating, an owner, a closure action, and computed coverage before and after those closures.

Use when

You suspect requirements, tests, data, environments, or automation have holes and need to prove exactly where — with impact — rather than asserting “coverage looks thin”.

Skip when

You need a full requirement decomposition — use 01-requirement-analysis-RICEPOT.md. Gap analysis compares; it does not extract.

1

Read the framework before you paste anything

The Role never supplies the missing answer, only the missing piece and its impact. That is what separates a gap register from a to-do list of guesses.

R
RoleWho the model is and the standard it is held to.
I
InstructionsThe numbered procedure. This is the part that must not be softened.
C
ContextThe only section you edit per run — product, sources, constraints.
E
ExampleA locked sample row showing the exact expected shape.
P
ParametersAnti-hallucination rules: determinism, exact fallback phrases, allowed values.
O
OutputFixed sections in a fixed order with fixed columns.
T
ToneHow the answer should read. No praise, no filler.
Rule of thumb. R, I, E, P, O and T stay as written. Only C — Context changes between runs. If you find yourself editing I, P or O, the template is being used for the wrong task.
2

Prepare the inputs first

A gap analysis is only as meaningful as the two artefacts it compares. Name both, precisely.

  • Baseline artefact — the requirements, PRD, or spec with IDs. This is what everything is compared against.
  • Comparison artefact — test cases, implementation, automation suite, or whatever should satisfy the baseline.
  • Owners roster — names or roles, so gaps can be assigned without inventing owners.
  • Prior gap list — if one exists, so reconciliation is by ID rather than memory.
  • Product and release — the scope the percentages apply to.

Most common mistake. Giving two artefacts that are not comparable — a PRD against a Jira epic, for example. The register then fills with documentation gaps rather than coverage gaps, and the percentages mean nothing.
4

Audit the output against the contract

Six sections. Coverage is reported twice on purpose: what is true today, and what would be true once the named closures land.

SectionRequiredShape
Scope of AnalysisYesBaseline, comparison set, method, date
Gap RegisterYesTable, 9 columns, unique GAP- IDs
Coverage Before/AfterYesArea | Baseline Items | Covered | Coverage % | After Closures %
Top 5 PrioritiesYesRanked list with rationale
Reconciled Prior GapsYesPrior GAP ID | Current Status | Evidence; may say “None”
Assumptions and LimitsYesBullets on what was not examined

Gap types are closed list: Requirement, Test Coverage, Data, Environment, Automation, Documentation, Process. Impact rating is 3-point: Release-blocking / High / Low, each with a one-line reason. Every row needs type, impact, owner, closure action, status.

6

Run the self-check before you trust the output

Seven checks. The two that matter most are the nine populated fields per row, and coverage recomputed from counts.

  • Baseline and comparison artefacts are named explicitly.
  • Every gap row has all nine fields populated.
  • Every impact rating has a reason.
  • Coverage percentages recomputed from counts.
  • No gap contains a guessed answer.
  • Prior gap reconciliation is done by ID, not by memory.
  • Assumptions section states what was not examined.
Fastest sanity check. Pick a gap row and ask “who closes this, and what is the next physical action?” If either answer is missing, the row is not actionable.
7

Fix the failure, not the whole prompt

SymptomRule breachedCorrection to send
A gap row contains the answer rather than the hole.Never fill a gap.“Move the proposed answer into Assumptions and keep the row Open.”
An impact rating has no reason.Reason per rating.“Add the one-line reason it matters.”
An owner was invented.No invented owners.“Write Not supplied. and flag it in the register.”
Two distinct gaps share one row.Do not merge gaps.“Split into separate GAP IDs.”
Coverage percentage was asserted.Computed from counts.“Recompute from Covered over Baseline Items and show the arithmetic.”
No baseline named.Baseline is mandatory.“State the baseline and comparison artefact in Scope of Analysis.”

Gap IDs are the unit of follow-up. Assign them, track them, and reconcile them by ID each cycle — re-describing the same gap in fresh words is how gaps survive for months.

9

Turn it into a skill

Create skills/gap-analysis/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: gap-analysis
description: Compare a baseline artefact against what exists, producing a typed gap register with impact ratings, owners, closure actions, and computed coverage before and after closure. Use when requirements, coverage, environment, or automation may have holes.
---

Trigger phrases: “gap analysis”, “what’s missing from our coverage”, “compare PRD to test cases”, “find the holes”.

Procedure: define baseline → enumerate items → compare → classify gaps → rate impact → assign owners → closure actions → coverage math → priorities → reconcile → assumptions → self-check.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
