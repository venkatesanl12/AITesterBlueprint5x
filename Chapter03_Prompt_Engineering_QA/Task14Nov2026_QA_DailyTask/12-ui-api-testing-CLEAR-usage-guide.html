UI and API Testing — CLEAR reference guide

Template file12-ui-api-testing-CLEAR.md
FrameworkCLEAR
TaskCombined UI, API and hybrid verification
Guide12 of 17

What it does. Designs and records UI cases, API cases, and hybrid consistency cases for one feature — each API case asserting status, body shape, and a field value, each negative case naming the layer that should reject it.

Use when

A feature must be verified at both layers, and you need proof that the UI reflects what the API actually returned rather than what it was supposed to return.

Skip when

Only screen behaviour matters — use 02-test-case-design-RICEPOT.md. Adding API cases you cannot call adds noise, not coverage.

1

Read the framework before you paste anything

CLEAR works here because the Limits list is where hallucination is fenced: no invented endpoints, fields, headers, or status codes — ever.

C
ContextWhat is being run, on which build, with which evidence.
L
LimitsThe fence: allowed statuses, allowed scope, what may not be invented.
E
ExamplesSample rows showing the exact status and evidence shape.
A
ActionThe single deliverable you want returned.
R
ReviewThe checks the model must pass before returning the answer.
Rule of thumb. Limits are the whole point of CLEAR — they stop the model awarding an unearned pass. Only C — Context changes between runs; never relax L to get a longer answer.
2

Prepare the inputs first

The contract is the critical input. Without an OpenAPI spec or sample responses, the API cases become gaps — which is the correct outcome, not a failure of the template.

  • UI details — URL, screen, and the flows in scope.
  • API base URL and endpoints — supplied, not assumed.
  • Contract — OpenAPI spec or real sample request/response pairs.
  • Auth method — token type and header name, as placeholders only.
  • Environment and seed data — build, browser, known IDs and records.

4

Audit the output against the contract

Six sections. Hybrid cases are the ones people skip and the ones that catch silent failure — a green UI over a broken response.

SectionRequiredShape
Coverage MapYesRequirement | UI Case IDs | API Case IDs | Hybrid Case IDs
UI Test CasesYesID | Screen | Action | Expected Element State | Confidence
API Test CasesYesID | Method | Path | Payload | Expected Status | Body Assertion | Rejecting Layer
Hybrid Consistency CasesYesID | Flow | UI Expectation | API Expectation | Consistency Check
Environment and AuthYesPlaceholders only
Blocked CasesYesID | GAP ID | Missing Contract Detail; may say “None”

Every API case asserts three things: HTTP status, response body shape, and at least one field-level value. Every negative case names the rejecting layer: client, gateway, or service.

6

Run the self-check before you trust the output

Six checks. The first and last are the same discipline from two angles: if you did not supply it, it must not appear.

  • No endpoint, field, header, or status code appears that was not supplied.
  • Each API case asserts status, body shape, and a field value.
  • Each negative case names the layer expected to reject.
  • Hybrid cases genuinely compare UI outcome to API outcome.
  • Auth tokens and credentials are placeholders.
  • Blocked cases cite a GAP ID rather than guessing the contract.
Fastest sanity check. Search the output for /api/ and 200. Every hit must map to something you supplied — otherwise the model has invented the contract.
