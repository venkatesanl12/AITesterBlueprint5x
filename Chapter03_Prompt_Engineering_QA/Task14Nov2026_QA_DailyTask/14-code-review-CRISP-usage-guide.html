Code Review — CRISP reference guide

Template file14-code-review-CRISP.md
FrameworkCRISP
TaskStructured review of application or test code
Guide14 of 17

What it does. Produces a located, classified, prioritised review: every finding cites a file and line, states the consequence, and proposes a minimal fix — with test quality assessed separately from production code quality.

Use when

You are reviewing application or automation code and want findings a developer can act on, rather than a list of opinions with no line numbers.

Skip when

You must also decide whether to merge, including CI, branch, and checklist gates — use 16-pr-merge-review-CRISP.md.

1

Read the framework before you paste anything

The Role is a senior engineer who cites lines and separates defects from preferences. That separation is what keeps a review actionable.

C
ContextThe situation and raw facts you supply. Per-run editable surface.
R
RoleThe judgement role the model takes on for this document.
I
InstructionsNumbered rules plus the explicit Do NOT list.
S
StyleHow terse, how structured, what vocabulary is banned.
P
ParametersHard limits: allowed scales, missing-data wording, length caps.
Rule of thumb. The Role decides the judgement, the Parameters decide the limit. If the output wavers, tighten the Parameters — not the Role. Only C — Context changes between runs.
2

Prepare the inputs first

The review can only cover what you supply. State the risk level and the standards, or the review will hold the code to standards it invented.

  • The code itself — the diff or the full file, complete. Truncated input must be declared unreviewed in the output.
  • Language, framework, version — so API suggestions match reality.
  • Intent — one line on what the change claims to do, so scope can be judged.
  • Standards — lint config or style guide, or “none” if you have none.
  • Test files — so test quality can be assessed rather than assumed.
  • Risk level — low, medium, or high. High risk justifies deeper scrutiny.

4

Audit the output against the contract

Five sections. Findings without a location are not findings, and test quality is a separate question from code quality.

SectionRequiredShape
Review ScopeYesWhat was reviewed, what was not, files/lines covered
FindingsYes# | Category | Location | Finding | Consequence | Suggested Fix
Test Quality AssessmentYesDo the tests prove the behaviour? Gaps listed
Security and SecretsYesExplicit statement; may say “None found”
VerdictYesApprove / Approve with comments / Request changes + reason

Categories are a closed list, in severity order: Blocker, Bug, Security, Performance, Maintainability, Style, Nit. A style issue is never a Blocker, and a preference must be labelled as a preference.

5

What a good run looks like

Filled excerpt from the template — each finding has a line number, a consequence, and a minimal fix. The fourth row is explicitly a nit, not a demand.

#CategoryLocationFindingConsequenceSuggested Fix
1BlockerLoginTest.java:47Password read from a hardcoded string literalCredential leaks into the repository and every CI logMove to env var / config and inject

The review also states separately whether the tests prove the behaviour — here they do not, because finding 2 means a failed login can pass.

6

Run the self-check before you trust the output

Seven checks. The asymmetry test — blockers are genuinely blocking, nits genuinely minor — is what keeps a review credible.

  • Every finding cites a real file and line from the supplied code.
  • Every finding states a consequence, not just a preference.
  • Blockers are genuinely blocking; nits are genuinely minor.
  • Hardcoded secrets, if present, are flagged as Blocker.
  • Test quality assessed separately from production code quality.
  • Anything outside the supplied diff is declared as not reviewed.
  • Verdict matches the severity mix.
Fastest sanity check. Count the Blockers. If more than two exist in a small change, the categories have drifted and preferences are being written as blockers.
7

Fix the failure, not the whole prompt

SymptomRule breachedCorrection to send
A finding has no line number.Location required.“Delete the finding or locate it in the supplied code.”
A preference is written as a defect.Preferences labelled.“Relabel as Style or Nit and mark it as a preference.”
A style issue is marked Blocker.Style is never a blocker.“Downgrade to Nit.”
Praise appears with no specifics.No praise padding.“Remove it, or attach the concrete reason it is good.”
Test quality is not assessed.Separate section required.“Add Test Quality Assessment with specific gaps.”
Files not supplied are treated as reviewed.Declare what was not reviewed.“List the unreviewed files under Review Scope.”

9

Turn it into a skill

Create skills/code-review/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: code-review
description: Perform a structured code review with located, classified, prioritised findings, consequences, minimal fixes, separate test-quality assessment, and a clear verdict. Use when reviewing application or automation code.
---

Trigger phrases: “review this code”, “code review for this change”, “is this test code good”, “check for issues in this file”.

Procedure: read whole change → scope declaration → findings by category → test quality → secrets check → verdict → self-check.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
