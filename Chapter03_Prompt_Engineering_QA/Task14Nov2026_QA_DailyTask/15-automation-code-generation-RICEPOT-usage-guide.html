How to Use This Template

Automation Code Generation — RICE-POT reference guide

Template file15-automation-code-generation-RICEPOT.md
FrameworkRICE-POT
TaskRunnable automation from supplied sources
Guide15 of 17

What it does. Generates automation code that compiles and runs without invented selectors, endpoints, or framework APIs — with assumptions and missing inputs declared in registers instead of being silently encoded in the code.

Use when

You are converting test cases into Playwright, Selenium, or API automation and the output has to actually run, not merely look plausible.

Skip when

You are generating test cases rather than code — use 02-test-case-design-RICEPOT.md. The anti-hallucination rules here are stricter and will strip case design.

1

Read the framework before you paste anything

RICE-POT is chosen for this task because the Parameters section is the strongest anti-invention fence available: no trace, no selector.

R
RoleWho the model is and the standard it is held to.
I
InstructionsThe numbered procedure. This is the part that must not be softened.
C
ContextThe only section you edit per run — product, sources, constraints.
E
ExampleA locked sample row showing the exact expected shape.
P

O

T

Rule of thumb. R, I, E, P, O and T stay as written. Only C — Context changes between runs. If you find yourself editing I, P or O, the template is being used for the wrong task.
2

Prepare the inputs first

The catalogue is what makes this template work. Selectors, endpoints, and the existing project conventions must be supplied, or the output is fiction with good formatting.

  • Stack and versions — language, framework, runner. Version matters for API availability.
  • Existing test file as reference — so conventions are copied, not invented.
  • Page objects, DOM snapshot, or OpenAPI — the supplied catalogue of selectors and endpoints.
  • Application URL and configuration approach — env vars, config file, or fixture.
  • Test cases to automate — with IDs, so each generated test maps to one case.
  • Credentials — as configuration placeholders only.

Most common mistake. Omitting the DOM snapshot. The model then invents plausible-looking IDs like login-username, the code compiles, and every test fails at the first findElement. Missing selectors belong in the register, not the code.
4

Audit the output against the contract

Six sections. The two registers are the honest part of the output: what was assumed, and what was missing.

SectionRequiredShape
Assumptions RegisterYesAssumption | Basis | Impact If Wrong; may say “None”
Missing-Input RegisterYesGAP ID | Missing Selector/Endpoint/API | Effect On Code; may say “None”
Generated CodeYesOne fenced block per file, target path as heading
Configuration RequiredYesVariable | Purpose | Example placeholder
How To RunYesExact command for the stated runner
Self-Verification NotesYesStatically checked vs needs a real run

Rules: zero invented selectors, zero hardcoded secrets, zero fixed sleeps. A missing locator becomes a TODO: locator not supplied (GAP-xx) comment plus a disabled test with a reason.

What a good run looks like

Filled excerpt from the template — the missing selector and missing endpoint are declared in the register, and the generated locators are traceable to the supplied DOM snapshot.

SectionContent
Missing-Input RegisterGAP-08 — no login endpoint or API contract supplied — API-layer login test cannot be written.
GAP-11 — dashboard success element not supplied — assertion target unknown; test marked @Disabled.
Generated Codepublic LoginPage open() { driver.get(config.baseUrl()); return this; }
Locators taken from the supplied DOM snapshot: By.id("login-username"), By.id("login-password"), By.id("js-login-btn").
Configuration RequiredbaseUrl, email, password — read from config.properties or env vars, never inlined.
How To Runmvn -Dtest=ValidLoginTests test
Self-VerificationStatically checked: imports match Selenium 4, no sleeps, each test independent. Not run: execution requires the real DOM and an account.

Note the last row. Generated code has not been executed, and the output says so rather than claiming green.

6

Run the self-check before you trust the output

Eight checks. The last one is the most important: generated code that has not been run must not be reported as passing.

  • Every locator appears in the supplied source catalogue.
  • No hardcoded credentials, URLs, or tokens.
  • No sleep or fixed timeout used for synchronisation.
  • Each test is independent and order-agnostic.
  • Assertions would fail on a real regression.
  • Every skipped or disabled test states its GAP reason.
  • Framework APIs match the stated version.
  • Generated code has not been claimed as passing — it has not been run.
Fastest sanity check. Grep the output for By.id(, By.cssSelector(, and http. Each hit must exist in the catalogue you supplied.
7

Fix the failure, not the whole prompt

SymptomRule breachedCorrection to send
A selector appears that is not in the catalogue.No trace, no selector.“Replace with a TODO comment, a GAP row, and @Disabled.”
Thread.sleep or waitForTimeout appears.No fixed sleeps.“Replace with an explicit wait on a supplied state.”
Credentials are inlined.Config or env only.“Move to config and reference the variable.”
Tests depend on execution order.Independence.“Reset state per test and remove shared mutable state.”
An assertion is a tautology.Assertions must detect regression.“Assert the observable outcome that would change on a regression.”
The output claims the tests pass.Code has not been run.“Replace with Self-Verification Notes: statically checked vs needs a real run.”

9

Turn it into a skill

Create skills/automation-code-generation/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: automation-code-generation
description: Generate runnable Playwright, Selenium, or API automation code using only supplied selectors, endpoints, and framework APIs, with assumptions and missing-input registers and no hardcoded secrets or fixed sleeps. Use when converting test cases into automation.
---

Trigger phrases: “automate this test case”, “write a Playwright test for”, “generate Selenium code”, “convert these cases to automation”.

Procedure: ingest catalogue → assumptions register → missing-input register → generate code per file → config spec → run command → static self-check → declare unverified.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
