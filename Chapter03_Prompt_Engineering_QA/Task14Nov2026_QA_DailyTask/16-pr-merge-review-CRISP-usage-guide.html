Guide16 of 17

What it does. Decides merge readiness from evidence rather than impression: a gate checklist marking Pass / Fail / Unknown, scope-creep detection, hygiene checks, test evidence assessment, and an explicit decision with the exact evidence needed.

Use when

You are the reviewer or approver on a pull request and the output has to be a decision someone can defend in an audit.

Skip when

You only need code-quality feedback — use 14-code-review-CRISP.md. Merge gates and code review are different questions.

1

Read the framework before you paste anything

The critical rule is that Unknown never counts as Pass. That single rule is what stops approvals on unverified assumptions.

C
ContextThe situation and raw facts you supply. Per-run editable surface.
R
RoleThe judgement role the model takes on for this document.
I
InstructionsNumbered rules plus the explicit Do NOT list.
S
StyleHow terse, how structured, what vocabulary is banned.
P
ParametersHard limits: allowed scales, missing-data wording, length caps.
Rule of thumb. The Role decides the judgement, the Parameters decide the limit. If the output wavers, tighten the Parameters — not the Role. Only C — Context changes between runs.
2

Prepare the inputs first

Approval is only as good as the evidence supplied. If CI status was not supplied, the gate is Unknown — and Unknown blocks the decision.

  • Repo and branches — source to target.
  • PR title and description — including whether it explains why.
  • Linked tickets — the scope baseline.
  • Diff or file list — complete. If truncated, the output must name what was not reviewed.
  • CI status and test evidence — job names and results, or say not run.
  • Merge policy — required approvals and required checks.

4

Audit the output against the contract

Seven sections. The decision must follow mechanically from the gate statuses, not from how the diff reads.

SectionRequiredShape
Scope CheckYesTicket intent vs actual diff
Merge Gate ChecklistYesGate | Status | Evidence
Scope CreepYesFiles/areas outside ticket scope; may say “None”
Hygiene FindingsYesSecrets, debug code, TODOs, dead code; may say “None found”
Test Evidence AssessmentYesProven vs claimed-but-unproven
DecisionYesApprove / Approve with follow-ups / Request changes / Block
Follow-upsYesItem | Owner | Suggested Ticket; may say “None”

Gate statuses are limited to Pass / Fail / Unknown. Decisions are limited to the four values. Any Fail or Unknown must state the exact evidence or fix that would clear it.

What a good run looks like

Filled excerpt from the template — one Fail and one Unknown drive the decision, and each states what is needed to proceed.

No debug logging left inFailSystem.out.println at LoginPage.java:52

Decision: Request changes. One Fail (debug logging) and one Unknown (CI status). To proceed: remove the println at LoginPage.java:52 and attach the CI job result.

6

Run the self-check before you trust the output

Seven checks. Treat the CI line as the canary — if CI is Unknown and the decision is Approve, the gate model was not applied.

  • Every gate has Pass / Fail / Unknown with evidence.
  • CI status treated as Unknown unless supplied.
  • Scope creep assessed against the linked ticket, not against taste.
  • Secrets and debug code explicitly checked.
  • Decision is consistent with the gate results.
  • Unreviewed files declared.
  • No test result asserted that was not supplied.
Fastest sanity check. Read the decision, then count the Fail and Unknown gates. Approve with any Unknown outstanding is a contract breach, not a judgement call.

9

Turn it into a skill

Create skills/pr-merge-review/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: pr-merge-review
description: Decide pull request merge readiness with a gate checklist covering scope, tests, CI, secrets, debug code, and reversibility, returning Approve, Approve with follow-ups, Request changes, or Block. Use when reviewing or approving a PR for merge.
---

Trigger phrases: “review this PR”, “is this ready to merge”, “PR approval checklist”, “merge gate check”.

Procedure: read ticket + diff → scope check → gate checklist → hygiene scan → test evidence → decision → follow-ups → self-check.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
