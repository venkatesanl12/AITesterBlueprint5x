FrameworkCLEAR
TaskArea-by-area coverage assessment
Guide17 of 17

What it does. Reports coverage area by area, separating requirement coverage from assertion coverage, ranking uncovered areas by risk, and stating plainly what the measurement cannot tell you.

Use when

Someone asks “are we covered enough to release?” and the answer must distinguish a requirement having a test from a test actually asserting the requirement.

Skip when

You need requirement-level traceability for an audit — use 06-rtm-RICEPOT.md. Coverage sufficiency and traceability are different questions.

1

Read the framework before you paste anything

The Limits section is doing real work here: it forbids one whole-system percentage and forbids crediting a test with coverage it never asserts.

C
ContextWhat is being run, on which build, with which evidence.
L
LimitsThe fence: allowed statuses, allowed scope, what may not be invented.
E
ExamplesSample rows showing the exact status and evidence shape.
A

R
ReviewThe checks the model must pass before returning the answer.
Rule of thumb. Limits are the whole point of CLEAR — they stop the model awarding an unearned pass. Only C — Context changes between runs; never relax L to get a longer answer.
2

Prepare the inputs first

Coverage needs a source of truth and an actual test list. Tool output is optional — but if it is absent, the output must say the figures are requirement-based, not line-based.

  • Coverage type — functional, code, API, risk-based, or mixed. This changes the method.
  • Source of truth — requirements list, codebase, or endpoint list.
  • Existing tests — the test list or coverage report.
  • Tool output — JaCoCo, Istanbul, coverage.py, or say none supplied.
  • Known untestable areas — so they are excluded openly rather than silently counted as gaps.
  • Release criticality — which areas must be covered before release.

4

Audit the output against the contract

Six sections. The two percentage columns are deliberately separate, because a test that runs without asserting is not coverage.

SectionRequiredShape
Coverage Scope and MethodYesType, source of truth, limitation statement
Coverage by AreaYesArea | Items | With Tests | Req Coverage % | With Assertions | Assertion Coverage % | Notes
Risk-Ranked Uncovered AreasYesRank | Area | Gap | Risk | Pointer
Release-Critical AssessmentYesWhich uncovered areas block release and why
Coverage LimitationsYesWhat this measurement cannot tell you
SummaryYesOverall figures, as ranges if heterogeneous

Requirement coverage and assertion coverage are never merged into one number. Percentages are computed from counted rows. Suggestions are limited to a one-line pointer per gap — this is an assessment, not a test design.

6

Run the self-check before you trust the output

Seven checks. The separation of the two coverage columns is the whole discipline — every other check supports it.

  • Every percentage recomputed from the row counts.
  • Requirement coverage and assertion coverage reported as distinct columns.
  • No test credited for behaviour it does not assert.
  • Risk ranking puts release-critical gaps first.
  • Measurement limitations stated explicitly.
  • No single misleading whole-system percentage.
  • Suggestions limited to pointers, not full test designs.
Fastest sanity check. Pick the highest coverage number and open one of those tests. If it does not assert the behaviour it is credited with, the assertion column is inflated.

9

Turn it into a skill

Create skills/test-coverage-assessment/SKILL.md, paste the frontmatter below, use the template's prompt block as the body, then add the output contract and self-check verbatim.

---
name: test-coverage-assessment
description: Assess functional, code, or API coverage area by area, separating requirement coverage from assertion coverage, ranking uncovered areas by risk, and stating measurement limits. Use when judging whether testing is sufficient before release.
---

Trigger phrases: “test coverage report”, “how much is covered”, “coverage gaps for this module”, “are we covered enough to release”.

Procedure: confirm coverage type → enumerate items → map tests → verify assertions → compute both percentages → risk rank gaps → release-critical callout → limitations → self-check.
One framework per file. Do not merge this with another framework's skeleton. Blended sections make the contract ambiguous and break the SKILL.md conversion.
