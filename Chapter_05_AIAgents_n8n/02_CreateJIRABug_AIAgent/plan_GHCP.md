# Jira Bug-Ticket Agent — Implementation Plan

## Goal

Build an AI agent that a QA engineer can use through a web chat to turn rough
bug notes into a clear, Jira-ready bug report. The agent asks follow-up
questions when required information is missing, shows the complete draft, and
creates a Jira issue only after the QA engineer explicitly confirms it.

## Confirmed MVP decisions

- **Jira:** Jira Cloud
- **Issue type:** Bug
- **Chat experience:** Web chat
- **Create policy:** Preview first; create only after QA confirmation
- **Jira site:** `https://venkatdwqa-1792319096211.atlassian.net/`
- **Jira project:** `AIBluePrint5x` (confirm whether this is the project key or
  project name before configuring the workflow)
- **LLM:** Groq with `openai/gpt-oss-120b` is the intended model; verify model
  availability and approve the provider's data handling before using real QA
  reports.
- **Authentication direction:** Use Jira authentication; decide whether this
  means each QA user's own Jira identity or a restricted automation account.
- **Evidence:** Screenshot/log attachments are in MVP scope.
- **Bug-report guidance:** Reuse
  [Template1_Basic_Bug_Report.md](../../Chapter03_Prompt_Engineering_QA/02_reuse-templates-bugs/Template1_Basic_Bug_Report.md)
  and
  [Template6_anti-hallucination-reminder.md](../../Chapter03_Prompt_Engineering_QA/02_reuse-templates-bugs/Template6_anti-hallucination-reminder.md).
- **LLM data-handling constraints:** Not decided.

## Recommended approach

Use n8n as the workflow and integration layer. For the first usable version,
use n8n's chat trigger/chat interface as the web entry point rather than
building a separate web application. Keep the workflow modular so a custom
website can replace or wrap the chat entry point later if needed.

### Conversation and workflow

1. QA starts a conversation and describes the issue in their own words.
2. The agent extracts evidence-backed fields and identifies gaps. It must not
   invent a root cause, error message, environment, expected behavior, or
   reproduction step.
3. The agent asks focused follow-up questions for required or materially
   useful missing details. Unknown values stay explicitly unknown; they are
   never silently filled in.
4. The agent produces a structured draft using the confirmed bug-report
   template:
   - Summary/title
   - Environment
   - Severity/impact
   - Steps to reproduce
   - Expected result
   - Actual result
   - Evidence and uploaded attachments
   - Any additional Jira-required fields confirmed during discovery
5. The chat displays the full draft and offers clear **Create**, **Edit**, and
   **Cancel** choices. No Jira write happens before explicit confirmation.
6. On confirmation, n8n validates the Jira fields and creates one Bug issue in
   the configured project.
7. The agent reports success with the Jira key/link, or explains the failure
   and preserves the draft so QA can retry or edit it.

### Suggested n8n building blocks

- **Chat Trigger:** Receive messages and maintain the conversation.
- **AI Agent / LLM:** Extract and refine the draft under the evidence-only
  rules.
- **Structured output/parser and validation:** Keep the draft in a predictable
  schema and check mandatory fields before submission.
- **Jira Cloud node or Jira REST API request:** Create the issue only after
  confirmation. Resolve project key, issue type, and required/custom fields
  from the Jira instance instead of guessing.
- **Conditional routing:** Separate clarification, preview, confirmed create,
  cancel, and error paths.

Treat the model's output as untrusted input. Validate it and enforce the
confirmation gate in the workflow itself; do not rely on prompt instructions
alone to prevent premature issue creation.

## Jira-ready draft contract

Use a stable internal draft object before mapping fields into Jira. A first
version can contain:

| Draft field | Behavior |
|---|---|
| `summary` | Concise, factual title based only on QA-provided information |
| `environment` | Record supplied environment details; otherwise ask or mark unknown |
| `severity` | Describe user/business impact; do not guess the Jira priority |
| `stepsToReproduce` | Preserve only steps supplied or confirmed by QA |
| `expectedResult` | Ask for the requirement/source when it is not stated |
| `actualResult` | Describe the observed behavior from QA's evidence |
| `evidence` | List supplied evidence and associate permitted uploaded files with the Jira issue |
| `projectKey` / `issueType` | Fixed/configured for the MVP, not generated by the model |
| `priority`, `labels`, `components`, custom fields | Map only after Jira options and team rules are confirmed |

Keep the conversational draft separate from Jira's final payload. The workflow
should map and validate the payload immediately before the create operation.

## Phased delivery

### Phase 0 — Resolve configuration and policy

- Confirm the Jira site and the actual project key.
- Inspect the project's Bug create screen and identify mandatory fields,
  custom fields, allowed values, and any required issue links.
- Agree how severity/impact maps to Jira priority.
- Select an approved LLM/provider and confirm what QA data may be sent to it.
- Choose the Jira authentication method and account. Use a least-privilege
  account restricted to the required project and issue-creation permissions.
- Decide access control for the chat and the exact Jira authentication/reporting
  identity.
- Define attachment limits, accepted file types, storage/retention, and how
  uploaded evidence is sent to Jira and the LLM.

**Exit:** A field mapping, access/authentication decision, and data-handling
decision are documented; a human QA owner approves the ticket template.

### Phase 1 — Draft-only conversation

- Create the n8n workflow and chat experience.
- Implement evidence extraction, clarification, draft generation, and edit/
  cancel behavior.
- Reuse the repository's bug-report structure and anti-hallucination rules.
- Do not connect an issue-creation action yet.

**Exit:** QA can turn representative free-form reports into editable drafts,
and missing details are asked about rather than invented.

### Phase 2 — Jira preview and confirmed creation

- Configure Jira credentials using n8n's credential storage; never place
  tokens in workflow prompts, chat responses, or committed files.
- Map validated draft fields to the Jira project's actual create-issue schema.
- Implement the agreed attachment flow with validation and appropriate
  access/retention controls.
- Add the explicit confirmation gate, cancel path, success response, and
  actionable error handling.
- Prevent accidental duplicate submission when a confirmation is retried.

**Exit:** A confirmed draft creates one Jira Bug with the expected field values;
cancelled or unconfirmed drafts create no issue.

### Phase 3 — Pilot and hardening

- Pilot with the QA user and a small set of real, non-sensitive examples.
- Review draft quality, clarification burden, Jira mapping, and failure cases.
- Add approved attachment handling, more issue types, or a custom chat UI only
  after the MVP is reliable and separately agreed.

## Acceptance criteria

- QA can access the chat only through the agreed access-control method.
- The agent produces a readable preview in the agreed Jira bug format.
- The agent asks a focused question when a required field or essential fact is
  missing, and explicitly marks unknown information rather than fabricating it.
- The preview includes all mapped Jira fields and is editable or cancellable.
- No issue is created unless the QA user confirms the displayed draft.
- A confirmed valid draft creates exactly one Bug in the configured project.
- The agent returns the created Jira key and link after success.
- Jira validation/auth/API failures are reported clearly; the draft is not
  discarded and no success is claimed.
- Credentials are stored outside source files, and the LLM/data policy is
  approved before real QA data is used.
- Supported attachments are handled according to the agreed file, privacy,
  and retention rules and are associated with the created issue.

## Risks and controls

| Risk | Control |
|---|---|
| The model invents details to make a report appear complete | Evidence-only rules, explicit unknowns, clarification, and human review |
| Jira rejects a draft due to required/custom fields | Discover the project's create schema and validate mapped values before submission |
| Duplicate issues after retries | Use a confirmation/submission state and prevent reprocessing the same confirmation |
| Unapproved QA data is sent to an LLM | Select an approved provider and define data handling before pilot |
| Unauthorized users create issues through the chat | Require authentication/access control and least-privilege Jira permissions |
| Prompt content causes unintended tool actions | Enforce allowed actions and the create-confirmation gate in n8n routing, not only in the prompt |

## Open questions to answer before implementation

1. Is `AIBluePrint5x` the exact Jira **project key**, or the project name?
2. Can you provide the Bug create-screen field list or a sanitized example of
   a correctly completed Jira bug from this project?
3. Which fields are mandatory, and what are the team's approved values/rules
   for priority, severity, environment, components, labels, and custom fields?
4. Is Groq with `openai/gpt-oss-120b` approved for QA reports, and may the chat
   content include customer data, personal data, screenshots, or logs?
5. Should the web chat be available only to the QA person, or to a defined
   group? What sign-in/access-control method is expected?
6. Which identity should appear as the Jira reporter: the QA user's own Jira
   account or a dedicated automation account?
7. What attachment types and size limits are allowed, and how long may files be
   retained? May attachment contents be sent to the selected LLM?
8. Should the agent create only Bugs in the MVP, or should it also support
   another issue type later?

## Out of scope for the first version

- Creating issues without a human confirmation.
- Automatically diagnosing root cause or asserting unverified expected
  behavior.
- Supporting multiple Jira projects or issue types before the single-project
  Bug flow is proven.
- Building a separate custom web application unless n8n's chat experience
  cannot meet the access or UX requirements.
