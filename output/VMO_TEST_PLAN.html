1. Objective

Validate that the VWO login dashboard gives new and returning users a secure, accessible, responsive, and performant way to authenticate and reach the personalized VWO dashboard. Verify email/password login, session behavior, optional MFA and enterprise SSO, input validation, password recovery, user feedback, key integrations, and regression impact before release.

2. Scope

In scope

  • Login page rendering, VWO branding, light/dark themes, responsive behavior, and touch-friendly controls.
  • Email/password authentication, field validation on blur, email-format handling, and password requirement/strength feedback where applicable.
  • Remember Me persistence, secure session creation/expiration/termination, redirect to the personalized dashboard, and return to prior context where supported.
  • Optional MFA, configured enterprise SSO (SAML/OAuth or confirmed protocols), and social login providers only if enabled for the release.
  • Forgot-password and email-based recovery, reset-token lifecycle, password policy enforcement, and recovery errors.
  • Actionable authentication errors, loading states, success confirmation, registration/free-trial path, and login-support route.
  • Keyboard access, screen-reader semantics/ARIA, clickable labels, high contrast, and WCAG 2.1 AA-oriented accessibility checks.
  • Security verification of transport/session requirements and rate limiting in approved non-production environments; formal security testing remains specialist-led.
  • Page-load and concurrency performance against agreed measurable targets; integration and analytics event correctness.
  • Cross-browser/device coverage for the product-approved support matrix and regression of adjacent sign-up, onboarding, and dashboard entry paths.

Out of scope

  • Post-login VWO experimentation, personalization, analytics, and reporting features beyond verifying successful dashboard handoff and access.
  • Production penetration testing, live brute-force attempts, or use of real customer credentials/data.
  • Internal operation of third-party identity providers; validate the VWO integration in a provider sandbox, not the provider’s entire service.
  • Biometric authentication, adaptive/risk-based authentication, and Progressive Web App behavior, listed by the PRD as future enhancements.
  • Full marketing/onboarding platform testing beyond the login-to-registration/support handoff and agreed event integration.

The login dashboard is the primary entry point to VWO’s optimization platform for business users and enterprise teams. The PRD aims to minimize login friction while providing enterprise-grade security and accessibility.

4. Test Methodology

  • Functional, negative, boundary, and exploratory testing for login, recovery, and navigation.
  • Smoke, sanity, regression, and end-to-end testing of the critical new and returning user journeys.
  • UI, responsive, browser/device compatibility, keyboard, screen-reader, high-contrast, and WCAG 2.1 AA accessibility checks.
  • API/service integration testing for authentication, recovery, session, SSO, support, and analytics interfaces where available.
  • Security verification in a controlled QA/staging environment; specialist security review for penetration and compliance certification.
  • Performance/load testing and availability/SLO review using approved non-production traffic profiles.
  • Automation of stable smoke, core regression, and API flows; manual review for exploratory, assistive-tech, and identity-provider variations.

5. Test Approach

Functional and user journey

  • Validate first-visit rendering, free-trial registration route, and product announcement/theme controls.
  • Authenticate with valid credentials and verify a single successful transition to the correct personalized dashboard.
  • Try unknown account, incorrect password, blank fields, malformed email, whitespace, boundary-length values, locked/disabled account (if supported), and repeated failed attempts.
  • Verify validation timing (on blur), focus order, inline messages, form submission behavior, loading state, and duplicate-submit protection.
  • Verify Remember Me on/off across browser restart and session boundaries, according to confirmed product policy.
  • Verify MFA challenge/verification/recovery where enabled; verify SSO provider selection, redirect, callback, cancel, denial, and error recovery.
  • Verify password reset request and reset link/token flow, including invalid, expired, reused token and password-policy failures.
  • Verify login support route, success confirmation, dashboard redirect, return URL/context preservation, and safe behavior on back/refresh.

UI, responsive and accessibility

Compare with approved design across the supported browser/device matrix. Validate Light/Dark Mode, VWO brand elements, keyboard and touch controls, mobile keyboard type for email, zoom/reflow, contrast, labels, focus indication, accessible names, error announcement, and full keyboard navigation. Perform WCAG 2.1 AA evaluation with automated checks plus manual keyboard and screen-reader testing.

API, backend and integration

For confirmed interfaces, validate payload/schema, status codes, error mapping, authorization, rate limiting, session/token attributes, reset-token lifecycle, and UI/API consistency. Confirm that analytics events record permitted success/failure attributes without passwords, reset tokens, or other secrets. Validate SSO/social provider return paths using test tenants and sandbox accounts.

Security, performance and reliability

Verify HTTPS enforcement and secure cookie/session configuration using approved test tools and environment access. Check failure handling, session invalidation, rate-limit response and audit evidence without attempting unsafe production activity. Measure login page load against the PRD's 2-second target on an agreed standard connection. Exercise load profiles representing thousands of simultaneous login attempts once the exact concurrency, duration, success/error mix, and latency objectives are agreed. Review availability measurement against the 99.9% target over an agreed observation window.

6. Assumptions and Clarifications

  • PRD-provided capabilities are intended requirements; optional SSO, social login, and MFA are tested only when enabled and configured in the target release.
  • Product/Engineering will provide valid and invalid synthetic accounts, a dedicated MFA/SSO test tenant, email sandbox/mailbox access, and reset-token test support.
  • The 2-second page-load target applies to the login page on a standard connection; exact metric definition, location, cache state, and percentile need Product/Engineering confirmation.
  • “Thousands” of concurrent login attempts is not a testable load profile until peak concurrency, ramp-up, duration, geography, and latency/error thresholds are specified.
  • Timeout periods, Remember Me duration, password complexity, lockout behavior, session revocation, token lifetime, and error text are not numerically defined by the PRD; test against approved policy/configuration.
  • Supported browsers, OS versions, mobile breakpoints, high-contrast behavior, SSO/social providers, and analytics event schema are to be confirmed before execution.
  • Availability 99.9% is an operational SLO, not a short test-run assertion; validate via agreed monitoring/operational evidence over a defined period.
  • GDPR/CCPA and enterprise compliance require Product/Security/Legal acceptance criteria and evidence mapping; QA functional checks alone do not constitute certification.
  • Targets of 95%+ login success, 90%+ satisfaction, 20% support-ticket reduction, and improved retention/conversion are product/business KPIs requiring production analytics or user research, not pass/fail criteria for a single QA cycle.

8. Backup / Contingency Plan

  • If an external identity provider is unavailable, test provider behavior in its sandbox or controlled mock for VWO-owned handling; mark end-to-end provider cases blocked if the real integration cannot be validated.
  • If email delivery is unavailable, use an approved mail sandbox/test hook and do not claim end-to-end recovery sign-off without validating message delivery and token link behavior.
  • If the QA environment is unstable, pause unreliable end-to-end tests, record build/time/environment evidence, and use API-level checks only where they remain representative.
  • If load testing cannot run safely in the shared environment, move to an isolated performance environment or approved staged ramp-up; never generate uncontrolled production load.
  • If accessibility tooling or assistive technology is unavailable, execute keyboard/manual checks and leave the relevant assistive-technology coverage blocked for follow-up.
  • Escalate scope, policy, dependency, and release blockers to Product, Engineering, Security, and Release owners; record decisions and accepted risks.

12. Entry Criteria

  • PRD and acceptance criteria are approved and traceable to the implementation/build.
  • Unspecified authentication policies, SLO/load profile, platform support matrix, optional provider scope, and analytics schema are clarified.
  • Build is deployed to a stable accessible non-production environment; release/build identifiers and feature flags are known.
  • Test accounts, MFA/SSO sandboxes, controlled email, analytics test destination, and reset-token test data are ready.
  • Test cases and regression impact are reviewed; no unresolved requirement ambiguity blocks expected results.
  • Performance and security testing have written authorization, safe test limits, and isolated environment approval.

13. Exit Criteria

  • All planned critical and high-priority login, recovery, and dashboard-handoff cases are executed; all blocked/not-run cases have owners and documented disposition.
  • No open blocker or critical defect remains; high-severity issues are fixed or formally accepted by Product, Security, and Release as appropriate.
  • Functional regression for registration, sign-in, recovery, session handling, and dashboard transition is completed and passing.
  • Accessibility checks have no unresolved release-blocking WCAG 2.1 AA defects, or approved documented exceptions.
  • Security, performance, and integration results meet approved targets; gaps against unspecified PRD targets are explicitly dispositioned.
  • Automation runs for agreed stable critical flows; failures and waivers have documented explanations.
  • Execution summary, defect report, residual risks, and QA recommendation are shared and sign-off recorded.

15. Automation Testing Scope

Planned automation candidates

  • Smoke: login page renders, valid login reaches dashboard, invalid login is rejected, and sign-out/session boundaries behave as specified.
  • Regression: field validation, Remember Me policy, loading/error states, forgot-password request/reset, registration/support links, and redirect/context behavior.
  • API: authentication/recovery contracts, status/error cases, rate limiting under safe test conditions, and analytics payload schema/privacy assertions.
  • Configured integration happy/failure paths for SSO and MFA where provider test hooks enable deterministic execution.

Manual or specialist-led coverage

  • Exploratory usability, visual comparison, keyboard and screen-reader review, and assistive-technology compatibility.
  • Identity-provider UX variations or external flows that are unstable or disallowed for automation.
  • Formal penetration testing, compliance audit, and user satisfaction studies.

16. Regression Scope

  • Existing email/password authentication and Remember Me behavior.
  • Forgot-password, reset email, reset-token validity, password change, and subsequent login.
  • MFA and configured SSO/social login paths, including cancellation and failed provider return.
  • Registration/free-trial entry and onboarding handoff for new users.
  • Dashboard redirect, deep-link/return-context handling, existing user context, and unauthorized direct navigation.
  • Session persistence, expiry, logout, revoked session, and browser back/refresh behavior.
  • Theme, responsive layout, accessibility, analytics events, and support/help links.

17. Deliverables

  • Approved test plan and PRD-to-test traceability matrix.
  • Detailed test scenarios/cases and test-data/setup guidance.
  • Functional, integration, compatibility, accessibility, performance, and security verification evidence as applicable.
  • Defect report, retest outcomes, automation execution report, and regression report.
  • Final test summary and QA release recommendation including known issues and accepted risks.
